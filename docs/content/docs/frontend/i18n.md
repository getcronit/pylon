`usePages` resolves the locale on the server, before the page renders. Translated
copy is in the first byte of HTML — no flash, no swap after mount — and the client
hydrates with the locale the server chose, so the two can't disagree.

```ts title="pylon.config.ts"
import {useNodeServer, type PylonConfig} from '@getcronit/pylon'
import {usePages} from '@getcronit/pylon/pages/plugin'

export default {
  plugins: [
    usePages({
      origin: 'https://example.com',
      i18n: {
        locales: ['en', 'de', 'fr'],
        defaultLocale: 'en',
        catalogs: './messages'
      }
    }),
    useNodeServer()
  ]
} satisfies PylonConfig
```

That gives you `/pricing` in English and `/de/pricing` in German — **from one
`pages/` tree**. There's no `[locale]` folder and nothing to restructure.

## URLs

The default locale is served unprefixed and every other locale gets a prefix:

| URL | Locale |
| --- | --- |
| `/pricing` | `en` (the default) |
| `/de/pricing` | `de` |
| `/fr/pricing` | `fr` |

`/en/pricing` permanently redirects to `/pricing`, so exactly one URL is canonical.

Set `prefix: 'always'` to prefix the default locale too (`/en/pricing`), in which
case `/pricing` redirects the other way.

:::note
The unprefixed URL **is** the default-locale page — a real, indexable page, not a
redirect. That's what removes the need to guess a visitor's language before serving
anything. See [why negotiation never redirects](#negotiation-never-redirects).
:::

## Reading the locale

```tsx title="pages/layout.tsx"
import {useLocale} from '@getcronit/pylon/pages'

export default function RootLayout({children}: {children: React.ReactNode}) {
  const {locale} = useLocale()
  return (
    <html lang={locale}>
      <body>{children}</body>
    </html>
  )
}
```

`useLocale()` returns the active `locale`, the configured `locales` and
`defaultLocale`, `localeWasExplicit` (did the request state a locale, or did we
fall back?), and `suggestedLocale` — see [suggesting, not
redirecting](#suggesting-not-redirecting).

It works identically on the server and in the browser, because the client reads
the server's answer rather than consulting `navigator.language`.

## Messages

Catalogs live in the directory you configured, one file per locale. The
**default locale must be `.ts` with `as const`** — it's the type source:

```ts title="messages/en.ts"
export default {
  nav: {home: 'Home'},
  checkout: {
    total: 'Total: {amount} for {count} items',
    items: {one: '{count} item', other: '{count} items'}
  }
} as const
```

Translations can be `.ts` or `.json`. Use `satisfies SameShape<typeof en>` to make
a missing or misspelled key a compile error:

```ts title="messages/de.ts"
import type {SameShape} from '@getcronit/pylon/pages'
import type en from './en'

export default {
  nav: {home: 'Startseite'},
  checkout: {
    total: 'Gesamt: {amount} für {count} Artikel',
    items: {one: '{count} Artikel', other: '{count} Artikel'}
  }
} satisfies SameShape<typeof en>
```

Register the default catalog once so keys are typed everywhere:

```ts title="pylon.d.ts"
declare module '@getcronit/pylon/pages' {
  interface Register {
    messages: (typeof import('./messages/en'))['default']
  }
}
```

:::warning
It must be `interface Register { messages: … }`. `interface Catalog extends …` is
invalid TypeScript, and because `pylon.d.ts` is a declaration file, `skipLibCheck`
hides the error — the registration silently does nothing and every key resolves to
`never`.
:::

### Translating

```tsx
import {useTranslations} from '@getcronit/pylon/pages'

function Total({cents, count}: {cents: number; count: number}) {
  const t = useTranslations('checkout')   // namespace is optional
  return <p>{t('total', {amount: String(cents / 100), count})}</p>
}
```

Keys **and** their placeholders are checked against your catalog. All of these are
compile errors:

```tsx
t('totl', {...})                          // no such key
t('total', {amount: '12'})                // missing `count`
t('total', {amount: '12', count: 3, x: 1}) // no such placeholder
useTranslations('nope')                   // no such namespace
```

No codegen and no generated files — the types come from the catalog's literals, so
your editor is correct the moment you save.

A missing message renders its key and warns, rather than throwing or rendering
nothing.

### Plurals

A plural message is an object keyed by CLDR category:

```ts
items: {one: '{count} item', other: '{count} items'}
```

```tsx
t('items', {count: 7})   // "7 items"
```

`count` is required and must be a number — it selects the branch via
`Intl.PluralRules`, using the **active locale's** rules. Polish picks `few` for
2–4 where English says `other`. If a translation omits the selected category,
`other` is used.

### Formatting

```tsx
const {number, date, relativeTime} = useFormatter()

number(12.5, {style: 'currency', currency: 'EUR'})   // €12.50 · 12,50 €
date(new Date(), {dateStyle: 'long'})
relativeTime(-3, 'day')
```

These wrap `Intl` with the active locale bound, memoised per options.

### Full ICU

For select, ordinals or nested formats, plug in a formatter:

```ts title="pages/layout.tsx"
import IntlMessageFormat from 'intl-messageformat'
import {setMessageFormatter} from '@getcronit/pylon/pages'

setMessageFormatter((message, values, locale) =>
  String(new IntlMessageFormat(message, locale).format(values))
)
```

Call it at import time from a module **both** the server and the browser load —
a layout works well. Setting it in `pylon.config.ts` would apply to the SSR pass
only and mismatch on hydration.

### Fallbacks and payload size

A key missing from a translation falls back to the default locale. That's resolved
once on the server, so the browser receives one complete catalog — never two to
search through.

Catalogs are server-only. Only the active locale's messages reach the browser, as
data in the hydration payload; no catalog is ever bundled into your client
JavaScript.

## Localizing on the backend

Everything above translates in the browser bundle. When the *data itself* is localized — a
product name out of the database, a validation message from a resolver — the locale has to
reach the resolver.

It does, automatically. Every document `useData` compiles carries the active locale, and a
resolver reads it with `getLocale()`:

```ts title="src/index.ts"
import {getLocale, Pylon} from '@getcronit/pylon'

export default new Pylon({
  graphql: {
    Query: {
      productName: async (id: number): Promise<string> => {
        const locale = getLocale() ?? 'en'

        // How you store translations is your choice — a per-locale row here.
        const translated = await ProductTranslation.objects
          .filter({productId: id, locale})
          .first()
        if (translated) return translated.name

        return (await Product.objects.get({id})).name
      }
    },
    Mutation: {}
  }
})
```

```tsx title="pages/product/page.tsx"
const data = useData()
return <h1>{data.productName({id})}</h1>   // German on /de, French on /fr
```

Nothing is passed at the call site. With `i18n` configured, compiled operations carry
`@inContext`:

```graphql
query page_0($__locale: String) @inContext(locale: $__locale) {
  product(id: 1) { name }
}
```

`getLocale()` returns `undefined` when the operation states no locale — it means the caller
did not ask, so the resolver decides what neutral means rather than being handed a guess.

`getInContext()` returns everything the directive carried, for when more than the locale is
needed:

```ts
import {getInContext} from '@getcronit/pylon'

const {locale} = getInContext()
```

You can use the directive by hand too, from any GraphQL client:

```graphql
query @inContext(locale: "de") { product(id: 1) { name } }
```

### Why not just read the request?

Two reasons, and they're the reason this is a directive rather than a header.

**A resolver runs in a different request than the page.** The SSR pass reaches GraphQL through
an in-process `POST /graphql`, which is its own request with its own context. The page's
`context` — locale included — is not in scope there. And after hydration there is no page
request at all: a refetch is a plain `POST /graphql` from the browser. A header-based design
would be locale-correct during SSR and locale-blind afterwards, which is worse than not having
it, because it works in exactly the situation you'd test.

**It would break the cache.** `pylon-query` keys its store on `documentId ~
variablesHash(variables)`. With the locale in a header, `/de` and `/fr` would send identical
documents with identical variables and collide on one entry — one language serving the other's
data. In the document, the locale is part of the key:

```
qd09ab19da988723b~1emsiz4    →  {"serverGreeting": "Server: hallo"}
qd09ab19da988723b~1emubph    →  {"serverGreeting": "Server: bonjour"}
```

Same document, different variables hash. Shopify's Storefront API uses the same directive for
the same reason.

:::note
`@inContext` is server-side context, and `context` from `useRequestContext` is page-render
state. They are not redundant — a resolver cannot see the latter, and a page does not need
the former.
:::

## Switching language

`<Link>` stays inside the current locale, so ordinary navigation needs no changes:
on `/de`, `<Link href="/pricing">` resolves to `/de/pricing`.

Add `locale` to cross:

```tsx
<Link locale="de">Deutsch</Link>                     {/* this page, in German */}
<Link href="/pricing" locale="fr">Tarifs</Link>      {/* a specific page */}
```

A cross-locale link is a full page load, deliberately: the other language is a
different document, with its own `<html lang>`, copy and hydration payload.

## Discoverability

With `origin` set, every localized page gets the full alternate cluster in
`<head>`, alongside its canonical:

```html
<link rel="canonical" href="https://example.com/de/pricing" />
<link rel="alternate" hreflang="en" href="https://example.com/pricing" />
<link rel="alternate" hreflang="de" href="https://example.com/de/pricing" />
<link rel="alternate" hreflang="fr" href="https://example.com/fr/pricing" />
<link rel="alternate" hreflang="x-default" href="https://example.com/pricing" />
```

Every locale carries the identical cluster — that's what makes it bidirectional and
self-referential — and each locale is its own canonical. Error responses get
neither tag.

`origin` is required and is configuration, not read from the request: these tags
need absolute URLs, and behind a proxy the `Host` header can't be trusted to build
them from.

### The canonical is not an i18n feature

It is listed here because the two appear together, but the canonical needs only
`origin` — a single-locale app gets one too. Only the alternate cluster needs
`i18n`, because only it needs to know the locale basenames.

### Emitting your own — `canonical: false`

The default canonical is the page's own URL, which is right for most pages and
always safe. It is derived from the request path, though, and two things it
cannot know sometimes make it wrong:

- **which query parameters matter.** `?page=2` is a different set of items and
  belongs in the canonical; `?colour=red` is a filtered view of the same set and
  does not. From here they are indistinguishable.
- **that two routes serve one thing** — a product at `/products/x` and at
  `/collections/y/products/x` — so one should nominate the other.

Turn it off and render your own:

```ts title="pylon.config.ts"
usePages({origin: 'https://example.com', canonical: false})
```

```tsx title="pages/products/[handle]/page.tsx"
<link rel="canonical" href={`https://example.com/products/${handle}`} />
```

:::warning[Rendering yours *alongside* Pylon's does not work]
React appends `<link>` to `<head>` rather than replacing it, and does not
deduplicate by `id` or `key` — so the page carries two canonicals, and search
engines discard conflicting ones outright. That is worse than a
wrong-but-single default, and it is why this is a flag rather than an override.
:::

`hreflang` is unaffected: keep the alternates Pylon emits and make sure your
canonical agrees with them. A page that canonicalises elsewhere while
advertising alternates contradicts itself, and the cluster may be discarded.

Your [sitemap](/docs/frontend/routing) expands too. Declare a URL once and every
locale's version is emitted, each carrying the alternates:

```ts title="pages/sitemap.ts"
export default function sitemap() {
  return [{url: '/pricing', changefreq: 'weekly'}]
}
```

Write a URL already prefixed (`/de/about`) and it's left exactly as you wrote it.

## Negotiation never redirects

A cookie or `Accept-Language` never changes which URL is served. This is a
correctness decision, not a preference: Googlebot sends **no** `Accept-Language`
header at all, and Bingbot, GPTBot, ClaudeBot and PerplexityBot generally don't
either. A site that redirects on that header sends every crawler to its default
language, and the rest of the site goes only partly discovered — by search engines
and by LLMs alike.

Redirects that do happen (`/en/pricing` → `/pricing`) depend only on the path and
your config, so a crawler and a visitor are always sent to the same place.

### Suggesting, not redirecting

When a request hints at a different locale than the URL, that hint arrives as
`suggestedLocale` — render an offer and let the visitor choose:

```tsx
const {suggestedLocale} = useLocale()

{suggestedLocale && (
  <Link locale={suggestedLocale}>Continue in {suggestedLocale}</Link>
)}
```

## Validating a locale

`hasLocale` narrows a `string` to one of your configured locales — useful when a
locale reaches you from somewhere untyped, like a form field or an API payload:

```tsx
import {hasLocale} from '@getcronit/pylon/pages/plugin'

const locales = ['en', 'de', 'fr'] as const

function switchTo(candidate: string) {
  if (!hasLocale(locales, candidate)) return notFound()
  // `candidate` is now 'en' | 'de' | 'fr'
}
```

## Cookie mode

For authenticated app UI, where URLs carry no SEO value, the cookie can decide
instead:

```ts
i18n: {locales: ['en', 'de'], defaultLocale: 'en', routing: 'cookie'}
```

One URL then serves every language. Use it only behind a login — with nothing to
canonicalise, a crawler sees a single-language site.

## Naming a route after a locale

A top-level route whose name is a configured locale — `pages/de/` alongside a `de`
locale — can't be reached: `/de` serves the German home page. Pylon warns at boot
and names both fixes: rename the route, or use `prefix: 'always'`, where
`/en/de` reaches it.

Only the top-level single segment collides. `/docs/de` and `/de/de` are both fine.
