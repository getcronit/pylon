A Pylon project is a single TypeScript application that produces a backend, a
database layer, and (optionally) a frontend. The layout is small and predictable.

## A typical project

```text title="my-app/"
my-app/
├─ src/
│  ├─ index.ts          # the entry — exports `default new Pylon(...)`
│  ├─ worker.ts         # optional — background-job worker entry
│  └─ apps/             # optional — composable feature modules
│     ├─ blog.ts
│     └─ shop.ts
├─ pages/               # optional — usePages React frontend
│  ├─ layout.tsx        # root layout (renders <html>/<body>)
│  ├─ page.tsx          # the "/" route
│  └─ posts/
│     └─ [id]/page.tsx  # "/posts/:id"
├─ migrations/          # generated migration files
├─ public/              # static assets served as-is
├─ pylon.config.ts      # plugins: database, identity, queues, pages, serving
├─ pylon.d.ts           # type augmentation
├─ tsconfig.json        # extends @getcronit/pylon/tsconfig.pylon.json
└─ .pylon/              # generated build output (git-ignored)
```

## The files that matter

### `src/index.ts` — the entry

The one file Pylon's compiler reads. It has exactly one default export:

```ts title="src/index.ts"
export default new Pylon({graphql, db?, queues?, gate?, basePath?})
```

The compiler introspects the `.graphql` property to derive the schema; at runtime
the same object serves resolvers. For larger apps, this file
[composes smaller apps](/docs/apps/overview): `new Pylon().compose(blog, shop)`.

### `pylon.config.ts` — plugins and serving

Build- and run-time wiring lives here, separate from your API. It's where you add
the database, identity, queues, and frontend plugins — and the
`strategy: 'last'` plugin that owns serving:

```ts title="pylon.config.ts"
import type {PylonConfig} from '@getcronit/pylon'
import {useDatabase} from '@getcronit/pylon/db/plugin'
import {useIdentity} from '@getcronit/pylon/auth/plugin'
import {serve} from '@hono/node-server'

export default {
  plugins: [
    useIdentity(myAuthProvider),
    useDatabase(),
    {name: 'serve', strategy: 'last', setup: app => serve({fetch: app.fetch, port: 3000})}
  ]
} satisfies PylonConfig
```

See the full [Configuration reference](/docs/reference/config).

### `pages/` — the frontend

If you use [usePages](/docs/frontend/overview), this directory is your file-based
router: directories are URL segments, `page.tsx` is a route, `layout.tsx` wraps a
subtree, and `[id]` / `[...slug]` are dynamic segments. See
[Routing & Pages](/docs/frontend/routing).

### `migrations/` — schema history

Generated by `pylon db diff` and applied by `pylon db migrate`. In
[apps mode](/docs/apps/overview), each app gets its own subdirectory, applied in
dependency order. See [Migrations](/docs/data/migrations).

### `.pylon/` — generated output

The build directory. Pylon does **not** bundle your server into a single file — it
emits `server.mjs` (an unbundled entry that imports your app, mounts the GraphQL
handler and plugins, and serves), `schema.graphql` (the derived schema), `client/`
(the typed query client), and, from `pylon build`, `src/` (your transpiled source).
It's regenerated on every build and should be git-ignored — never edit it by hand.

## Conventions

- **One entry, one default export.** The compiler reads `src/index.ts`'s default
  export. Keep it the composition root.
- **Models register on construction.** A model is a plain class listed in an
  app's `db.models` — constructing the `Pylon` (or any app it composes) registers
  them, so keep your apps reachable from the entry's default export.
- **`$`-prefixed members are private.** A field or method whose name starts with
  `$` (like `$save`) persists and runs but is hidden from the generated GraphQL
  schema.
